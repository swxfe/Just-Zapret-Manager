# Тесты JZM

Все команды выполняются из активного Linux checkout `/home/me/src/just-zapret`.
Полный локальный набор запускается через `just test`; сборка кода — `just bundle`, полного релиза с отдельным архивом ресурсов — `just dist`.

## Структура

```text
tests/
├── run.sh / run.py  общий запуск локального набора
├── mocks/           исполняемые подмены команд, HTTP/procd и fault injection
│   ├── e2e/         SSH, SCP и QEMU для офлайн-проверок оркестратора
│   ├── integration/ гонки и ошибки публикации файлов
│   ├── packages/    opkg, apk и содержимое архивов
│   ├── safety/      ошибки системных команд и транзакционного worker
│   └── uninstall/   прерывание удаления
├── fixtures/        статические входные данные: BAT и каталоги стратегий
├── setup/           подготовка временных роутеров, ubus и эмулятора
├── support/         параллельный runner, bytecode shim, утверждения и firewall hook
├── unit/            домены, GitHub, пакеты, стратегии, источники, state, устройства, файлы
├── integration/     сценарии приложения и драйверы ucode/PTY
│   └── cases/       конфигурация, списки, бэкапы, стратегии, сеть, установка, восстановление
├── safety/          транзакционные отказы, сигналы, откат и удаление
├── http/            реальные локальные HTTP/TLS-проверки нативного клиента
├── performance/     навигация без fork/popen/записей и контроль повторных чтений
└── e2e/
    ├── run.sh       запуск QEMU, загрузка скриптов и сбор отчётов
    ├── host/        загрузчик релизов, отчёты и их офлайн-тесты в selftests/
    └── router/      общая подготовка, тематические cases/ и диспетчер гостевых тестов
```

В `fixtures/` лежат только данные. Подмена команды или сервиса относится к `mocks/`;
создание окружения и его очистка — к `setup/`; проверки поведения — к соответствующему набору.
Сгенерированные файлы и отчёты остаются в `/tmp/` или игнорируемой `.test-tmp/`.

## Скорость и диагностика

`just test` запускает независимые наборы параллельно (до четырёх workers по числу CPU).
Вывод каждого набора печатается целиком, с результатом и временем выполнения.
Ошибки дают ненулевой код завершения; оставшиеся наборы тоже выполняются.
SIGINT/SIGTERM/SIGHUP останавливают группы дочерних процессов и дают fixture время на очистку.

```sh
JZM_TEST_JOBS=1 just test       # последовательный прогон, в том числе selftests эмулятора
JZM_TEST_JOBS=2 just test       # ограничить нагрузку
JZM_TEST_COMPILE=0 just test    # повторять загрузку исходного main.uc на каждом вызове
```

По умолчанию `main.uc` со статическими импортами компилируется один раз в новый каталог
`/tmp/` текущим ucode. Тестовая обёртка подставляет этот bytecode только вместо точки
входа source launcher и transaction worker. Inline-программы, fault injection и
самостоятельный shell-бандл исполняются напрямую. Кеш между прогонами не сохраняется;
порядок интеграционных этапов и все проверки сохраняются. Отдельные shell-наборы
из списка ниже запускаются напрямую, без этой оптимизации.
В локальной проверке прерывания HTTP helper ждёт явного освобождения после сигнала,
с ограничением времени ожидания: фиксированная двухсекундная пауза не нужна.
Офлайн selftests эмулятора также распараллелены: каждому тесту принадлежат отдельные
каталог, SSH-порт и fake emulator. Настоящие QEMU-прогоны сохраняют эксклюзивный lock.

## E2E в QEMU

По умолчанию полный E2E распределяет все 36 гостевых сценариев между отдельными
Cudy WR3000P. Число эмуляторов выбирается по CPU и свободной RAM, максимум восемь.
Каждый стартует с чистого flash, заново устанавливает зависимости, менеджер,
Zapret и LuCI. Между эмуляторами разделяются только исходные образы и программы;
flash, каталог QEMU work, Unix-сокеты, SSH-порты и состояние роутера изолированы.

Сценарии распределяются по длительности предыдущего прогона, а внутри каждой группы
сохраняют исходный порядок. Удаление пакетов остаётся последним в своей группе.
Перед каждым следующим сценарием выполняются прежнее восстановление и health checks.
Варианты blockcheck (успех, ошибка, INT/TERM/HUP, остановленный сервис) выполняются
отдельно, с теми же проверками конфигурации, state, lock и сервиса. SSH-соединение
каждой VM переиспользуется между этапами и закрывается при очистке.
Общий lock не допускает запуска второго полного E2E поверх активного.

    just test-e2e                       # автоматический выбор, до восьми QEMU
    E2E_WORKERS=2 just test-e2e           # два отдельных роутера
    E2E_WORKERS=1 just test-e2e           # исходный последовательный прогон на одном роутере

Для явного числа workers доступны значения 1–8; для параллельного запуска число проверяется по доступной RAM
до загрузки VM. Базовый SSH-порт задаётся E2E_SSH_PORT (по умолчанию 8022), следующие
workers используют соседние порты. Все порты проверяются до первого запуска QEMU.
В параллельном режиме предел ожидания SSH — 90 секунд; E2E_BOOT_TIMEOUT переопределяет его.

В .test-tmp/e2e/latest.txt указан общий отчёт. Рядом находятся plan.json с распределением
сценариев, timing.json с общим временем, TAP/JSON и отдельные отчёты в shards/worker-N/.
Успех требует полного покрытия: ни одного пропуска, дубликата или постороннего сценария,
успешных результатов всех workers и маркеров завершения всех гостей. Ошибка или
SIGINT/SIGTERM/HUP сохраняют неуспешный отчёт и завершают все собственные QEMU.

## Отдельные наборы

```sh
sh tests/unit/run.sh
sh tests/integration/run.sh
sh tests/integration/packages.sh
sh tests/safety/transactions.sh
sh tests/safety/uninstall.sh
sh tests/http/run.sh
sh tests/e2e/run.sh selftest
```

`integration/run.sh` явно задаёт порядок этапов: они используют один временный роутер
и проверяют последовательный жизненный цикл приложения. Файлы из `integration/cases/`
подключаются этим runner и отдельно не запускаются. PTY, session-cache, manager-update
и performance получают подготовленное окружение от него.

`e2e/run.sh payload router` собирает единый гостевой скрипт из `router/common.sh`,
`router/cases/` и `router/run.sh`. На роутер передаётся готовый скрипт, исходники проекта
там не нужны. Подготовка эмулятора: `just emulator-setup`; полный прогон QEMU: `just test-e2e`.

`tools/check.sh` рекурсивно проверяет синтаксис shell и Python, компилирует точки входа
ucode вместе с импортируемыми модулями и запускает ShellCheck. Подключаемые shell-этапы
анализируются в контексте своих runner, а гостевые этапы — в собранном payload.
Новый этап нужно добавить в явный список соответствующего runner.

`tests/assets/mutate.py` создаёт повреждённые и небезопасные архивы для проверки
установщика: пути вне назначения, ссылки, дубликаты, неверные размеры и SHA256.
Тесты также инъецируют отказ публикации манифеста после записи ассетов и проверяют
полный откат. Стратегии, фейки и списки тестируются с HTTP-провайдером, который
запрещает любые запросы. Парсеры upstream сохранены в сборочных инструментах,
их модульные проверки запускаются вместе с остальными тестами.
